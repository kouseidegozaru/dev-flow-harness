# ファネルの定義・計測・計算

## 1. 段階

サービスに合わせて名前と定義を変えてよい。ただし、各段階は **人数で数えられる出来事** で定義する (「興味を持った」は段階にしない)。

| 段階 | 定義の例 | よくある取り方 |
|------|----------|----------------|
| 認知 | 広告の表示・検索結果への表示・SNS の表示 | 広告の管理画面、Search Console |
| 訪問 | サイトへの訪問 (ユニークユーザー) | Vercel Web Analytics、Google Analytics、アクセスログ |
| 登録 | アカウントの作成・無料トライアルの開始・問い合わせの送信 | アプリの DB (users テーブルの作成日)、フォームの送信記録 |
| 有効化 | 価値を初めて体験した (例: 最初のプロジェクトを作った、初回の予約を受けた) | アプリの DB・イベントの記録 |
| 契約 | 契約の定義 (baseline.md) を満たした | Stripe などの決済 (初回の支払いの成功)、契約の DB |
| 継続 | 契約後 N か月目も契約している (解約していない) | 決済のサブスクリプションの状態、解約の記録 |

- B2B で営業が入るなら、登録と契約の間に「商談」「見積り」を足す
- 純増を目標にするなら、継続 (解約) も同じ重みで見る。新規を増やしても解約が多ければ、契約数は増えない

## 2. ボトルネックの見積もり

段階 i の率を r_i (= 段階 i の人数 / 段階 i−1 の人数) とすると、契約数は

```
契約数 = 訪問 × r_登録 × r_有効化 × r_契約
```

段階 k の率を r_k → r_k' に上げたときに増える契約数は

```
増える契約数 = 現在の契約数 × (r_k' / r_k − 1)
```

r_k' には、同じ種類のサービスの一般的な水準か、過去の最高値か、摩擦を取ったときの見込みを使い、どれを使ったかを書く。
**増える契約数が一番大きい段階がボトルネック。** 率が低いだけでなく、上流の人数が多い段階ほど効く。

例: 訪問 10,000 → 登録 300 (3%) → 有効化 120 (40%) → 契約 24 (20%)。

- 登録の率を 3% → 4% にすると 24 × (4/3 − 1) = +8 件
- 有効化の率を 40% → 60% にすると 24 × (60/40 − 1) = +12 件 ← ボトルネック
- 契約の率を 20% → 25% にすると 24 × (25/20 − 1) = +6 件

継続 (解約) の改善は、`毎月の解約数の減り = 契約中の数 × (解約率の今 − 改善後)` で、新規と同じ単位 (件/月) に直して比べる。

## 3. 数字の取り方

自分で取れるものは自分で取る。どこから取ったかを baseline.md に書く (次の判定でも同じ方法で取るため)。

| 出どころ | 取り方 |
|----------|--------|
| Stripe (MCP) | 期間内の初回の支払いの成功・新しいサブスクリプションの数・解約 (canceled) の数。読み取りだけを使う |
| アプリの DB (Supabase などの MCP、または DB のクライアント) | 登録・有効化の出来事の件数を、作成日で期間を絞って数える。**SELECT だけを使い、書き込まない** |
| Vercel Web Analytics (MCP) / Google Analytics | 訪問者数、ページごとの訪問者数 (料金ページ・登録ページ) |
| ユーザーに聞く | 上のどれでも取れないとき。値に `ユーザー申告` と付ける |

計測が入っていない段階があれば、何を入れれば測れるか (イベント名・記録する場所) を具体的に書き、計測の追加を施策の候補にする。

## 4. 摩擦のチェックリスト (コードと画面を読んで確かめる)

| 段階 | 確かめること |
|------|--------------|
| 訪問 → 登録 | トップに「誰の何を解決するか」が 1 文で書かれているか。料金が見つかるか。登録ボタンが最初の画面に見えるか。表示が遅くないか (目安: LCP 2.5 秒以内)。スマホで崩れないか |
| 登録 | 入力項目の数 (最初に要らない項目を求めていないか)。ソーシャルログインの有無。メール確認で止めていないか。エラーの文が直し方を言っているか |
| 登録 → 有効化 | 登録の直後に何をすればよいかが分かるか。空の画面 (データ 0 件) に次の一歩があるか。サンプルデータ・テンプレートの有無。有効化までの手順の数 |
| 有効化 → 契約 | 無料の範囲と有料の差が分かるか。有料の機能に触れたときに案内が出るか。決済の画面までの手順の数。支払い方法の種類。トライアルの終わりの前に知らせるか |
| 契約 → 継続 | 支払いの失敗 (カードの期限切れ) を拾って知らせるか。解約の理由を聞いているか。使われていない契約者に気づけるか |

## 5. 判定に要る人数と、差の確かめ方

### 必要な人数 (A/B の 1 群あたり)

率が p から p + d に上がったことを見分けるのに要る人数の目安 (有意水準 5%、検出力 80%):

```
n ≈ 16 × p × (1 − p) / d²
```

例: 登録 → 契約の率 p = 0.04 を d = 0.01 上げたい → n ≈ 16 × 0.04 × 0.96 / 0.0001 ≈ 6,144 人 (1 群)。

- 判定日 = 開始日 + (n × 群の数 ÷ 1 日あたりの対象の人数) 日。曜日の偏りをならすため、最短でも 1 週間、週の単位で切り上げる
- 人数が足りない (判定まで 8 週間を超える) ときは、A/B をやめて前後比較にし、小さな改善ではなく **大きく変える施策** (d を大きく見込めるもの) を選ぶ。
  前後比較は季節・広告などの影響が混ざるので、同じ期間の外部要因 (キャンペーン・休日) を施策カードに書く

### 差の確かめ方 (2 つの率の比較)

```
p1 = x1 / n1、 p2 = x2 / n2、 p = (x1 + x2) / (n1 + n2)
z = (p2 − p1) / √( p × (1 − p) × (1/n1 + 1/n2) )
```

|z| ≥ 1.96 なら、差は偶然の範囲を超えている (有意水準 5%)。計算は手で済ませず、スクリプト (python・node など) で行い、式と値を施策カードに残す。
