# contract-growth: 契約数を増やす改善サイクル

勘で施策を打たず、**数字でボトルネックを特定 → 一番効く施策から 1 つずつ試す → 結果で採否を決める** を繰り返すスキル。
状態はすべて `docs/growth/` のファイルに残し、コンテキストがクリアされても、そこから続きを始められるようにする。

引数: `$ARGUMENTS`

## 1. 状態を読んで分岐する

`docs/growth/` を見て、次の表で始める手順を決める。引数があれば、引数を優先する。

| 状態 / 引数 | 始める手順 |
|-------------|------------|
| `docs/growth/baseline.md` がない | 2. 目標と前提 |
| baseline.md の「現状値」が空 / `diagnose` | 3. ファネルの計測と診断 |
| `experiments.md` に `実行中` も `候補` もない / `ideas` | 4. 施策を出して選ぶ |
| `run <EXP-ID>`、または `承認済み` の施策がある | 5. 施策を実行する |
| `review <EXP-ID>`、または `実行中` の施策の判定日を過ぎた | 6. 効果を判定する |
| `実行中` の施策が判定日前 | 状況 (施策・判定日・途中の数字) を伝えて終える。途中の数字で判定しない (§6 の注意) |
| `status` | baseline.md の目標と現状値、experiments.md の一覧を要約して終える |

## 2. 目標と前提を決める (対話)

**最初に読む**: [references/funnel.md](references/funnel.md)、テンプレート [references/templates/baseline.md](references/templates/baseline.md)

- 先に自分で調べる (質問しない): `docs/01-vision.md` (成功指標・対象ユーザー・制約)、`docs/02-requirements/`、
  コードベース (登録・料金・決済・解約の画面と処理、計測のタグ・イベント)、つながっている MCP (Stripe・Supabase・Vercel など)
- 調べても分からないことだけを **1 回に 1 問、推奨回答と理由を添えて** 聞く (AskUserQuestion を使ってよい)。「それで」で推奨どおりに進む
- 決める論点と、決まったと言える状態:

  | 順 | 論点 | 決まったと言える状態 |
  |----|------|----------------------|
  | 1 | 契約の定義 | 何をもって「1 契約」と数えるかが 1 文で言える (例: 有料プランの初回決済の成功。無料トライアルの開始は数えない) |
  | 2 | 目標 | 数と期限 (例: 月の新規契約 30 → 50 件を 3 か月後に)。純増 (新規 − 解約) か新規だけかも決まっている |
  | 3 | 対象と商品 | 誰に何をいくらで売るか (プラン・価格・トライアルの有無) |
  | 4 | 計測の方法 | ファネルの各段階の数字をどこから取るか (funnel.md §3)。取れない段階があればそう書く |
  | 5 | 制約 | 触ってよい範囲 (コード・料金・メール・広告)、予算、使ってはいけない手段。「特になし」も明示的に確認する |

- 決まったら `docs/growth/baseline.md` をテンプレートから作り、ユーザーに見せて承認を得る

## 3. ファネルの計測と診断

**最初に読む**: [references/funnel.md](references/funnel.md)

1. funnel.md §1 の段階 (認知 → 訪問 → 登録 → 有効化 → 契約 → 継続) を、このサービスに合わせて定義する
2. 直近の期間 (目安: 4 週間。少なければ 3 か月) の各段階の人数を取る。MCP・DB・解析ツールから自分で取れるものは自分で取り、
   取った方法 (クエリ・ツール・期間) を baseline.md に書く。取れないものはユーザーに聞くか、`不明` と書く
3. **コードを読んで、契約までの道筋の摩擦を列挙する** (funnel.md §4 のチェックリスト)。実際に画面を動かせるなら動かして確かめる (`run` スキルなど)
4. 段階ごとの率を出し、funnel.md §2 の式で **「この段階を改善したら増える契約数」** を見積もり、ボトルネックを 1〜2 段階に絞る
5. 計測が欠けていて判断できない段階が、ボトルネックの候補になるなら、**計測の追加を最初の施策にする** (測れないものは改善を判定できない)
6. baseline.md の「現状値」「摩擦の一覧」「ボトルネック」を更新し、要点 (どこで何人落ちていて、直すと何件増えそうか) をユーザーに伝える

## 4. 施策を出して選ぶ

**最初に読む**: [references/levers.md](references/levers.md)、[references/guardrails.md](references/guardrails.md)、
テンプレート [references/templates/experiments.md](references/templates/experiments.md)

1. ボトルネックの段階について、施策を 5〜10 個出す。出どころ: 手順 3 で見つけた摩擦、levers.md のカタログ、過去の学び (`docs/growth/log.md`)。
   **guardrails.md に当たるものは出さない**
2. 各施策を仮説の形で書く: 「<変えること> をすると、<段階> の率が <今> → <見込み> になる。なぜなら <根拠>」
3. ICE で点を付ける (levers.md §1)。Impact は funnel.md §2 の式で出した「増える契約数」で付ける
4. 点の高い順に並べて `docs/growth/experiments.md` に `候補` として書き、上位 1〜3 個を推奨としてユーザーに選んでもらう。
   選ばれたものは `承認済み` にし、施策カード `docs/growth/experiments/<EXP-ID>.md` を作る (テンプレート [references/templates/experiment.md](references/templates/experiment.md))
5. 同時に実行するのは、**同じ段階に効く施策を 1 つまで** (効果が混ざって判定できなくなるため)

## 5. 施策を実行する

1. 施策カードに、判定の基準を **実行の前に** 書く: 主指標 (1 つ)、守る指標 (解約率・返金・問い合わせ・表示速度など)、
   成功の基準 (例: 登録 → 契約の率が 4.0% → 5.0% 以上)、方式 (A/B か前後比較か)、必要な人数と判定日 (funnel.md §5)
2. 計測を先に入れる: 主指標と守る指標が取れることを確かめてから、変更を入れる
3. 変更の種類で進め方を分ける:

   | 種類 | 進め方 |
   |------|--------|
   | コードの変更で、dev-flow を使っているプロジェクト (`.devflow/state.json` がある) | dev-flow が `done` なら `/dev-flow change <施策の内容>` で仕様の変更として入れる。dev-flow が進行中なら手を出さず、施策カードに「dev-flow の完了後に入れる」と書いて止まる |
   | コードの変更で、dev-flow を使っていない | 施策用のブランチで、テストを書いてから実装する。変更は施策に要る分だけにする。A/B なら、振り分けと記録をフィーチャーフラグなどで切り替えられるようにする |
   | コード以外 (メール・料金・広告・営業資料・SNS) | 文面・手順・設定値を成果物として作り、ユーザーに渡す。**メールの送信、料金・プランの変更 (Stripe などへの書き込み)、広告の出稿・予算の変更は、内容を見せてユーザーの明示的な承認を得てから** 行う |

4. 施策カードの状態を `実行中` にし、開始日と判定日を書く。experiments.md の状態欄も合わせる
5. 変更と docs をコミットする (クラウドのセッションでは push する)

## 6. 効果を判定する

1. 判定日を過ぎたら、手順 3 と同じ方法で主指標と守る指標を取る。**判定日の前に、途中の数字を見て止めない・採用しない** (偶然の差を効果と取り違えるため)
2. funnel.md §5 の式で、差が偶然の範囲を超えているかを確かめる
3. 判定する:
   - **採用**: 成功の基準を満たし、守る指標が悪くなっていない → 変更を残す (A/B なら全員に出す)
   - **棄却**: 基準に届かない、または守る指標が悪くなった → 変更を戻す
   - **延長**: 人数が足りない → 判定日を 1 回だけ延ばす。2 回目は、その時点の数字で採用か棄却を決める
4. 施策カードに結果と学び (なぜ効いた / 効かなかったと考えるか) を書き、`docs/growth/log.md` に 1 行足し、baseline.md の現状値を更新する
5. 結果をユーザーに伝え、手順 4 (次の施策) に戻るかを聞く

## 7. 共通のルール

- **数字の出どころを必ず書く。** 推測の値には `推定` と付け、推定だけで採否を決めない
- **ユーザーをだまして契約させる手段は、目標の達成に効くとしても使わない** ([references/guardrails.md](references/guardrails.md))。
  ユーザーから頼まれたときも、理由 (法令・信頼の損失) を伝えて代わりの施策を出す
- 外部への書き込み (メールの送信・料金の変更・広告・SNS への投稿) は、毎回、内容を見せて承認を得てから行う。前の承認を次に使い回さない
- 個人を特定できるデータ (メールアドレス・氏名・決済情報) は、集計に要る分だけ扱い、docs や会話に書き写さない (件数と率だけを書く)
- ユーザーへの報告・質問、docs はすべて日本語で書く
