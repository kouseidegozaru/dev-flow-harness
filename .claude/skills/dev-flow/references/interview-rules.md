# 対話フェーズ共通の詰め方ルール (企画・構想、要件定義、基本設計)

grill-me スタイルで仕様を徹底的に詰める。目的は「以降のフェーズがユーザーに質問せずに進められる」状態を作ること。

## 1. 質問の仕方

- **質問は 1 回に 1 つだけ。** 複数の論点があっても、最も上流 (他の決定を左右する) ものから 1 つずつ聞く
- 各質問には **推奨回答とその理由** を添える。ユーザーは「それで」と答えるだけで進めてよい
- 選択肢がある場合は 2〜4 個に絞り、推奨を先頭に置く (AskUserQuestion ツールを使ってよい)
- 質問の形式:

  ```
  Q<通し番号>. <質問> (論点: <決定ツリー上の位置>)
  推奨: <推奨回答>
  理由: <1〜3 行>
  ```

## 2. 質問しないこと

- コードベース、既存ドキュメント、前フェーズの成果物を調べれば分かることは質問せず、自分で調べる
- 一般的な慣習で決まり、プロジェクトに影響の小さいもの (例: ファイルの文字コード) は推奨で決めて、決定一覧に「既定で決定」と記録する
- ただし、既定で決めた項目も一覧で提示するので、ユーザーは後から覆せる

## 3. 曖昧な回答の掘り下げ

「いい感じに」「普通に」「適当に」「一般的な」「速く」「使いやすく」などは決定ではない。具体化するまで掘り下げる。

- 数値にする (件数、時間、サイズ、回数)
- 例を出して選んでもらう (「A のような表示か、B のような表示か」)
- 境界を聞く (「0 件のときは?」「上限を超えたら?」「同時に2人が操作したら?」)
- それでも決まらない場合は推奨値で決め、その旨を記録する

## 4. 決定ツリーの管理

決定事項を決定ツリーとして `.devflow/decisions/<phase>.md` に記録し、**1 つ決まるたびに更新する**。
コンテキストが圧縮・クリアされても、このファイルから再開できるようにするため (テンプレート: `templates/decisions.md`)。

- ノード = 論点。状態は `決定` / `未決定` / `スコープ外` / `既定で決定`
- 決定によって新たに生じた論点は子ノードとして追加する
- **未決定のノードがなくなるまでフェーズを終えない**

## 5. 全体像の提示

- 5 問ごと、または大きな論点が片付くたびに「決定済み / 未決定」の一覧を提示する
- 一覧は決定ツリーの要約でよい (決定済みは 1 行ずつ、未決定は残りの質問数の見込み付き)

## 6. スコープ外の扱い

スコープ外と判断した事項は黙って捨てず、「スコープ外」として **理由付き** で成果物に記録する。
ユーザーが話題にしたが採用しなかったアイデアも同様に記録する。

## 7. 承認前のレビュー (要件定義・基本設計。1 回だけ)

企画・構想では行わない (詳細設計は手順書 04 の design-reviewer で行う)。
成果物を書き終え、trace が exit 0 になったら、承認を求める前に `spec-reviewer` サブエージェントに **1 回だけ** レビューさせる。

1. `spec-reviewer` を起動し、対象フェーズとレビュー対象のファイルの **パスだけ** を渡す (中身は渡さない)。依頼文:

   > 対象フェーズ: <requirements | basic-design>。次のファイルをレビューせよ: <ファイルの列挙>。
   > 次のフェーズの担当がユーザーに聞かないと決められない点だけを、質問の形で挙げよ。

   ファイルが多い場合 (目安 15 ファイル超) は、関連の強いまとまり (機能領域ごと、画面群と API 群など) に分けて、
   まとまりごとに 1 体を並列で起動してよい。`index.md` はすべてのまとまりで共通に渡す
2. 指摘は、決定ツリーの「レビュー指摘」に `R<番号>` として登録する。複数のまとまりの指摘で同じ論点のものは 1 つにまとめる
3. 指摘を **1 つずつ** ユーザーに質問する (§1 の形式。報告の「質問」「推奨」「理由」を下敷きにし、自分で調べて分かることは質問しない)。
   他の指摘の答えを左右するものから聞く。回答を成果物と決定ツリーに反映する。回答で新たに生じた論点も同じく 1 つずつ詰める
   - 誤記・ID の振り忘れなど、ユーザーの判断が要らず一意に直せる指摘は、質問せずに直し、「既定で決定」として記録する
   - 指摘が誤り (成果物に既に書かれている、次のフェーズで決めるもの) なら、理由を添えて「対応不要」と記録する
4. 反映後に trace をもう一度実行し、exit 0 にする
5. **再レビューはしない。** 指摘をすべて反映したら、決定ツリーの「レビュー状況」を「反映済み」にして §8 に進む。
   中断から再開したときは「レビュー状況」を見て、レビュー済みなら起動し直さず、未対応の指摘の質問から続ける

## 8. フェーズの終わり方

1. 未決定ノード (未対応のレビュー指摘を含む) が 0 件であることを決定ツリーで確認する
2. 成果物のドラフト (大きい場合は index.md と各ファイルの要約) を提示する。レビュー指摘があったフェーズでは、指摘と対応の一覧も添える
3. **ユーザーの明示的な承認** (「承認」「OK」「これで進めて」など) を得る。承認前に修正依頼があれば反映して再提示する (再レビューはしない)
4. SKILL.md の「フェーズの終え方」に従って終了する
