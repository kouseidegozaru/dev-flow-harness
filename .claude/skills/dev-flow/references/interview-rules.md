# 対話フェーズ共通の詰め方ルール (企画・構想、要件定義、基本設計)

grill-me スタイルで仕様を徹底的に詰める。目的は「以降のフェーズがユーザーに質問せずに進められる」状態を作ること。

## 1. 質問の仕方

- **質問は 1 回に 1 つだけ。** 複数の論点があっても、最も上流 (他の決定を左右する) ものから 1 つずつ聞く
- 各質問には **推奨回答とその理由** を添える。ユーザーは「それで」と答えるだけで進めてよい
- 選択肢がある場合は 2〜4 個に絞り、推奨を先頭に置く (AskUserQuestion ツールを使ってよい)
- 質問の形式:

  ```
  Q<通し番号>. <質問> (論点: <決定ツリー上の位置>)
  推奨: <推奨回答>
  理由: <1〜3 行>
  ```

## 2. 聞くか、仮に決めるか (決定台帳)

聞く範囲は広げも狭めもしない。変わるのは「聞かずに決めたこと」と「聞いて決めた値」を、照合パターン付きで **決定台帳**
(`.devflow/decisions/ledger.md`) に 1 行ずつ残すこと。台帳に載った値は、後から 1 つの経路 (`override` / `amend`) で影響の範囲だけ直せる。

- コードベース、既存ドキュメント、前フェーズの成果物を調べれば分かることは質問せず、自分で調べる
- **仮に決めてよい (聞かない) もの**: 一般的な慣習で決まり、プロジェクトに影響の小さいもの (例: ファイルの文字コード、日付の書式) と、
  推奨が上流 (承認済みの成果物・ユーザーの発言) から一意に決まる値。推奨で決めて、台帳に `仮` の行を足す:

  ```bash
  pwsh -NoProfile -File scripts/devflow-state.ps1 ledger add -Kind 仮 -Topic '<論点>' -Value '<決めた値>' -Match '<照合>' -Basis '<根拠>'
  ```

- **従来どおり聞くもの**: 企画・構想 (01) の全論点。要件定義 (02) の機能の中身 (何を出すか・並び順・境界・空のとき・失敗のとき)。
  承認済みの決定の変更。お金・法令 (個人情報を含む)・セキュリティ・外部への送信や外部サービスの契約。照合パターンが書けない「形」の論点
  (画面・項目・コマンドの有無や構成)。推奨が一意に決まる技術的な論点に限り、1 回の AskUserQuestion に 4 問まで束ねてよい
- **聞いて決まった値も台帳に入れる** (`-Kind 確定`)。同じ照合・覆しの経路に乗せるため。「形」の論点で照合が書けないものは台帳に入れなくてよい
- 根拠 (`-Basis`) には、上流の ID (`REQ-…` など) か、ユーザーの発言の **逐語引用**「…」を書く。慣習で決めた `仮` の値 (上流に根拠がない) は
  `-Basis '慣習: <何の慣習か (例: 日付は ISO 8601)>'` と書く (使う側の要件 ID を根拠にしない。根拠が循環するため)。引用は `docs/01-vision.md` か
  決定ツリー (`.devflow/decisions/<phase>.md`) の質問ログに逐語で残っていること (`ledger check` と trace が確かめる)。
  そのため **質問ログの「回答」欄は、ユーザーの言葉をそのまま書く** (要約しない)
- 照合 (`-Match`) は、その値を他の値と区別できる部分と、派生値を含めて書く正規表現 (例: 上限 100 なら `100 文字|101 文字`、
  文字コードなら `BOM 付き|efbbbf`)。`UTF-8` のように別の意味の行にも当たる語だけにしない。バッククォートは使えない。
  機能の名前にもなる語 (`評価`・`★` など) は、タスク名や見出しにも当たるので、値の形 (`★[1-5]`、`評価は 1〜5`) に絞る
- その値を書いた成果物の行 (表の行・地の文・タスクのテストケース) には `決定: DEC-…` か `(DEC-…)` を書く。
  プログラムが出す値でない決定 (「外部に送らない」など) を test の要件の備考で引用してよい (Then にその値が現れなければ、印は求めない。§10)。照合に当たるのに DEC を書いていない行は
  trace が DEC-UNCITED にする。別の意味で同じ語を使う行には `DEC 対象外: DEC-…` と書く
- 決定ツリーの「既定で決定」は、台帳の `仮` の行の DEC を添えて書く (`既定で決定: <論点> → <値> (DEC-003)`)。決定ツリーの Q は従来どおり残す

## 3. 曖昧な回答の掘り下げ

「いい感じに」「普通に」「適当に」「一般的な」「速く」「使いやすく」などは決定ではない。具体化するまで掘り下げる。

- 数値にする (件数、時間、サイズ、回数)
- 例を出して選んでもらう (「A のような表示か、B のような表示か」)
- 境界を聞く (「0 件のときは?」「上限を超えたら?」「同時に2人が操作したら?」)
- それでも決まらない場合は推奨値で決め、その旨を記録する

## 4. 決定ツリーの管理

決定事項を決定ツリーとして `.devflow/decisions/<phase>.md` に記録し、**1 つ決まるたびに更新する**。
コンテキストが圧縮・クリアされても、このファイルから再開できるようにするため (テンプレート: `templates/decisions.md`)。

- ノード = 論点。状態は `決定` / `未決定` / `スコープ外` / `既定で決定`
- 決定によって新たに生じた論点は子ノードとして追加する
- **未決定のノードがなくなるまでフェーズを終えない**

### 決定の理由を成果物に残す

成果物だけを読む人 (次のフェーズの担当、レビュー担当、後日の見直し) には決定ツリーが見えない。
一般的な作り方と違う決定・安全側でない決定・あえて作らない決定 (例: 「PIN は 4 桁で単純なものも許す」「予約は 7 年で消す」) は、
その要件・設計の **備考に `決定: DEC-<番号>` を書く** (台帳の行に論点・値・根拠がある。台帳に載らない「形」の決定は従来どおり `決定: Q<番号> (<理由 1 行>)`)。
書かないと、見直しのたびに同じ点が「問題」として挙がり、決め直しになる (実際に、承認後の見直しで 27 件中 11 件がこれだった)。

## 5. 全体像の提示

- 5 問ごと、または大きな論点が片付くたびに「決定済み / 未決定」の一覧を提示する
- 一覧は決定ツリーの要約でよい (決定済みは 1 行ずつ、未決定は残りの質問数の見込み付き)

## 6. スコープ外の扱い

スコープ外と判断した事項は黙って捨てず、「スコープ外」として **理由付き** で成果物に記録する。
ユーザーが話題にしたが採用しなかったアイデアも同様に記録する。

## 7. 承認前のレビュー (要件定義・基本設計。1 回だけ)

企画・構想では行わない (詳細設計は手順書 04 の design-reviewer で行う)。
成果物を書き終え、trace が exit 0 になったら、承認を求める前に `spec-reviewer` サブエージェントに **1 回だけ** レビューさせる。

1. `spec-reviewer` を起動し、対象フェーズとレビュー対象のファイルの **パスだけ** を渡す (中身は渡さない)。依頼文:

   > 対象フェーズ: <requirements | basic-design>。次のファイルをレビューせよ: <ファイルの列挙>。
   > 次のフェーズの担当がユーザーに聞かないと決められない点だけを、質問の形で挙げよ。

   ファイルが多い場合 (目安 15 ファイル超) は、関連の強いまとまり (機能領域ごと、画面群と API 群など) に分けて、
   まとまりごとに 1 体を並列で起動してよい。`index.md` はすべてのまとまりで共通に渡す
2. 指摘は、決定ツリーの「レビュー指摘」に `R<番号>` として登録する。複数のまとまりの指摘で同じ論点のものは 1 つにまとめる
3. 指摘を **1 つずつ** ユーザーに質問する (§1 の形式。報告の「質問」「推奨」「理由」を下敷きにし、自分で調べて分かることは質問しない)。
   他の指摘の答えを左右するものから聞く。回答を成果物と決定ツリーに反映する。回答で新たに生じた論点も同じく 1 つずつ詰める
   - 誤記・ID の振り忘れなど、ユーザーの判断が要らず一意に直せる指摘は、質問せずに直し、「既定で決定」として記録する
   - 指摘が誤り (成果物に既に書かれている、次のフェーズで決めるもの) なら、理由を添えて「対応不要」と記録する
4. 反映後に trace をもう一度実行し、exit 0 にする
5. **再レビューはしない。** 指摘をすべて反映したら、決定ツリーの「レビュー状況」を「反映済み」にして §8 に進む。
   中断から再開したときは「レビュー状況」を見て、レビュー済みなら起動し直さず、未対応の指摘の質問から続ける

### レビュー指摘と決定の突き合わせ

指摘をユーザーに質問する前に、決定ツリーで同じ論点が既に決まっていないかを確かめる。ユーザーがはっきり決めたことを覆す指摘は、
質問せずに「対応不要 (決定: Q<番号>)」と記録し、成果物の備考に決定の理由が書かれていなければ書き足す (上の「決定の理由を成果物に残す」)。

## 8. フェーズの終わり方

1. 未決定ノード (未対応のレビュー指摘を含む) が 0 件であることを決定ツリーで確認する
2. 成果物のドラフト (大きい場合は index.md と各ファイルの要約) を提示する。レビュー指摘があったフェーズでは、指摘と対応の一覧も添える。
   **ユーザーが全部を読まなくても判断できるよう、最初に「承認の前に見てほしい決定」を 10 件以内で挙げる**:
   台帳のこのフェーズの `仮` の行 (聞かずに決めたこと) のうち利用者から見える振る舞いを変えるもの、
   `確定` のうち推奨のまま決めた (「それで」で決まった) もので、お金・法令・個人情報・セキュリティ・外部サービスの契約に関わるもの、§9 で「該当なし」にした観点。
   DEC と値を 1 行ずつ示す (承認後に変えたくなっても、DEC 単位で直せることを一言添える)。
   件数 (ID 数・ファイル数) が多いときは、その数も添え、承認は「この一覧を見た上で」で足りることを伝える
3. **ユーザーの明示的な承認** (「承認」「OK」「これで進めて」など) を得る。承認前に修正依頼があれば反映して再提示する (再レビューはしない)
4. SKILL.md の「フェーズの終え方」に従って終了する

## 9. 横断的な観点のチェックリスト (企画・構想と要件定義)

機能ごとに 1 問ずつ詰めると、機能をまたぐ観点が誰にも聞かれないまま抜ける (実際に、SEO・アクセス解析、特定商取引法の表記、
要配慮個人情報の同意、未成年の扱い、決済の結果が戻らないときの二重処理などが、承認の後で見つかった)。
要件定義では、成果物を書く前に次の各観点を決定ツリーのノードにし、「決定」「スコープ外 (理由付き)」「該当なし (理由付き)」のどれかにする。
企画・構想では、該当しそうな観点を「制約」と「スコープ外」に挙げておく。

| 観点 | 確かめること (該当するものだけ) |
|------|---------------------------------|
| 集客・計測 | SEO (検索エンジンに載せるページ、メタ情報、サイトマップ)、アクセス解析 (GA4 など)、検索エンジンの管理ツール (Search Console・Bing Webmaster)、SNS での共有表示 |
| 法令・表記 | 特定商取引法の表記、利用規約、プライバシーポリシー、業界の法令 (医療・金融・飲食など)、電子帳簿保存法・インボイス、アクセシビリティ |
| 個人情報 | 取得する情報と同意の取り方、要配慮個人情報 (健康・病歴など)、本人からの開示・訂正・削除の依頼、保持期間と削除 |
| 利用者の属性 | 未成年 (保護者の同意)、高齢者、外国語、障害のある利用者 |
| お金 | 金額の端数処理、税、返金・取消、二重課金の防止、外部の決済が成功したのに結果が戻らないとき、手数料、締め・日付の区切り |
| 時刻 | タイムゾーン、日付の区切り (0 時か営業日か)、祝日、夏時間、期限の判定 |
| 外部サービス | 外部サービスで自動化できそうな機能 (書誌・住所・地図・翻訳などの自動取得) を候補として挙げて、作るかを聞く (料金・キー登録・送る情報を添える。料金・キーの要否は記憶でなく公式のドキュメントで確かめる)。障害・遅延時の振る舞い、再送と冪等性、契約・審査・利用料の上限、API の利用制限 |
| 通知 | メールの到達 (送信元の認証・迷惑メール)、送れなかったときの扱い、配信停止 |
| 運用 | 障害の検知と連絡、バックアップと復旧、メンテナンスの告知、問い合わせ窓口、管理者の操作の記録 |
| 不正・悪用 | 総当たり、なりすまし、予約や在庫の買い占め、スパム登録、権限の昇格 |
| 公開・移行 | 公開の手順と環境 (本番・検証)、ドメイン、既存データの移行、リリースの段階 |

## 10. 受け入れ例の印 (要件定義。承認で凍結される)

受け入れ基準の Then の中で、**プログラムが出す値** をバッククォートで印す。承認時に `.devflow/examples.lock.json` に凍結され、
受け入れテスト (`tests/acceptance/`) の期待値と機械で照合される (受け入れテストの期待値側に、その値が無ければ警告になり、最終レポートで人が確かめる)。

| 書き方 | 意味 | 例 |
|--------|------|----|
| `` `値` `` | 出力にこの値がある | Then `` `登録しました: こころ` `` と表示する |
| `` `値` [DEC-003] `` | 台帳の DEC に依る値 (DEC を引用する test の要件で、Then にその DEC の照合に当たる値があるなら、その印が必須。無いと DEC-NOT-IN-EXAMPLE) | Then 先頭 3 バイトが `` `efbbbf` [DEC-003] `` |
| `` `!値` `` | この値が **無い** (否定印) | Then `` `!efbbbf` `` (BOM なし) |
| `` `a` → `b` → `c` `` | この順に並ぶ | Then `` `坊っちゃん` → `こころ` → `三四郎` `` の順 |

- 印は Then の中だけに付ける。Given / When の値 (入力・コマンド) には付けない (Then より前のバッククォートは数えない)。Then の中でコマンド名などを書くときはバッククォートで囲まない
- 値は、テストの期待値にそのまま書ける文字列にする (文言は一字一句。数値は単位を含めるか、テストの書き方に合わせる)
- 承認後に例の値を変えるのは `override` / `amend` を通したときだけ (変えてから `devflow-state.ps1 relock`。通さずに変えると trace が EXAMPLE-CHANGED にする)
